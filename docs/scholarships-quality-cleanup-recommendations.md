# Scholarships catalog — план очистки без удаления данных

Документ основан на аудите `reports/scholarships-quality/*` (snapshot `generatedAt` в `summary.json`).  
**Никаких DELETE/UPDATE из этого документа не выполняется** — только рекомендации и будущие политики.

---

## A. Общий диагноз базы

| Метрика | Значение |
|---------|----------|
| Всего записей | 17 211 |
| **good** (score ≥ 80) | 10 069 (**58.5%**) |
| **ok** (60–79) | 6 144 (**35.7%**) |
| **needs_review** (40–59) | 652 (**3.8%**) |
| **likely_trash** (0–39) | 346 (**2.0%**) |
| Уникальных нормализованных title | 16 920 |

**Вывод:** база **в целом здоровая**: **~94.2%** строк в зонах **good + ok**. Это не «мусорная» свалка, а крупный каталог с **ожидаемыми артефактами парсинга и агрегации**.

**Главные проблемы (не равно «мусор»):**

1. **Дубликаты по разным ключам** — до **5 494** строк затронуты хотя бы одним типом exact-дубликата (часто одна программа с разных landing pages, особенно **bigfuture** и агрегаторы).
2. **Просроченный `deadline_date`** — **3 896** строк (~22.6%): нормально для исторического каталога, но требует **политики отображения**, а не массового удаления.
3. **Верхушка ручной проверки** — `manual-review-top-200.csv` и **346** `likely_trash`: там смешаны **реальные проблемы**, **ложные срабатывания anti-keyword** (например «loan» в «student loan» контексте, «insurance» в названии стипендии), и **aggregator duplicates** (одинаковые названия направлений вроде Chevening с разных страниц **mastersportal**).
4. **Источники с коротким описанием** — **mastersportal** (~99% weak по аудиту), **scholarships_com** (~76% weak): это про **полноту полей**, а не обязательно про-off-topic контент.

---

## B. Что НЕ делать

1. **Не удалять массово все expired** — многие страницы могут быть полезны для SEO, редиректов и истории; часть дедлайнов обновляется сезонно.
2. **Не удалять все duplicate по URL без ручной проверки** — один и тот же URL может быть каноническим для нескольких slug legacy; обратное: разные URL могут указывать на **одну** программу (агрегаторы).
3. **Не отключать источник только из-за small sample** в `top_20_worst_sources` (например **9** или **5** строк) — высокий % suspicious там статистически нестабилен.
4. **Не запускать AI на все 17k** — дорого, шумно; имеет смысл только на узком срезе после эвристик (отдельное разрешение).
5. **Не делать массовый DELETE** вообще на первом этапе — политика сайта и юридические риски; предпочтительны **soft-hide**, **merge metadata**, **canonical slug**.

## C. Что делать первым (приоритет)

1. **Разобрать `likely_trash` (346)** — выгрузить список id, пройти чеклист: off-topic / сломанный парсер / дубликат агрегатора / ложный anti-keyword.
2. **Пройти `manual-review-top-200.csv`** — там сконцентрированы худшие score; паттерн: **mastersportal** + повторяющиеся названия + `parser_garbage` в отчёте (проверить, не HTML-мусор ли в description).
3. **Высокообъёмные источники с аномалиями** — см. раздел D: **bigfuture**, **scholarships_com**, **mastersportal**, **scholarships360**, **daad** (много `anti_keyword_hit` в CSV часто из-за URL/query, а не контента).
4. **Expired — отдельный поток** — политика отображения и флаги (раздел F), не смешивать с «мусором».
5. **Duplicate clusters — отдельный поток** — политика canonical + слияние дублей (раздел E), начинать с **`primary_url`** и **`norm_title + provider`**.

## E. Дубли — типы и безопасная политика dedupe

Типы (как в аудите `duplicates-exact.csv`, префиксы `duplicate_key`):

| Тип ключа | Смысл |
|-----------|--------|
| `primary_url:…` | Один канонический URL — часто **истинный дубль** записи. |
| `norm_title:…` | Одинаковое нормализованное название — может быть **много разных программ** (ложный дубль). |
| `title_provider:…` | Название + провайдер — сильнее, чем title alone. |
| `title_deadline:…` | Название + дата — сильный сигнал для сезонных программ. |
| `title_amount:…` | Название + сумма — полезно, но шумно при «Varies». |

**Near duplicates** (`duplicates-near.csv`) — похожие title внутри блока source + префикс слов; отдельная ручная валидация.

### Safe dedupe policy (без DELETE)

1. **Выбрать canonical запись** по **полноте**: description/summary, deadline, amount, provider, проверенный URL, `is_verified`, свежий `updated_at` / `last_seen_at`.
2. **Не удалять** побочные строки сразу: пометить миграцией (будущие поля вроде `duplicate_of_id` / `canonical_scholarship_id`) или **только после отдельного approval** выставить **`is_active = false`** для не-canonical.
3. **SEO / slug**: если страница уже индексируется — **301** на canonical listing или оставить slug с noindex на дубликате; не ломать внешние ссылки без редиректа.
4. Сначала **отчёт и dry-run SELECT** (`scripts/scholarships-cleanup-dry-run.sql`), затем маленькие батчи UPDATE под контролем.

## F. Expired — политика

| Условие | Рекомендация |
|---------|----------------|
| `deadline_date` в прошлом **&lt; 6 месяцев** | Оставить в каталоге с меткой **«Closed / Recently expired»** в UI; не считать мусором. |
| Просрочено **&gt; 12 месяцев** | **Скрыть из активной выдачи** (фильтр по умолчанию), карточка может оставаться по прямой ссылке или для админов — **без DELETE**. |
| Evergreen / rolling (нет достоверной даты) | Не помечать expired только из-за старого текста; улучшить парсинг `deadline_text` → `deadline_date`. |
| Есть **`deadline_text`**, нет **`deadline_date`** | Отдельная очередь **date extraction** (82 строки **missing_deadline** полностью — отдельный класс). |
